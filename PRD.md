# Product Requirements Document

## Product

- **Product name:** Arovia Clinic AI
- **Dashboard name:** Arovia Healthcare Dashboard
- **Assistant name:** Arovia Assistant
- **Tagline:** Care that understands you.
- **Current release:** Standalone interactive demo; no production backend or external integrations are connected.

## Problem and goals

Clinic staff need a single, calm place to review clinic operations and sample patient activity. Arovia Clinic AI demonstrates how appointment management, clinic records, schedules, conversations, and operational reporting can fit into one dashboard.

The current product must:

1. Run locally without Lovable or a hosted application builder.
2. Preserve the existing dashboard design and all ten dashboard screens.
3. Let users explore and modify sample data during a browser session.
4. Make demo data and inactive integrations unmistakable.
5. Leave a clear, secure path to future database, authentication, messaging, and AI services without implementing them in the frontend.

## Users

- **Clinic administrator:** Reviews appointments, patients, doctors, services, and clinic configuration.
- **Clinic staff:** Works with appointments, availability, and patient records.
- **Clinic owner or evaluator:** Reviews activity, analytics, example conversations, and the future integration status.

These are product personas, not authenticated roles in the current demo. There is no real sign-in or authorization.

## Product scope

### Available dashboard routes

| Route | Screen | Current capabilities |
| --- | --- | --- |
| `/` | Overview | Clinic summary, appointment activity, analytics highlights, and assistant connection status |
| `/appointments` | Appointments | Review and manage sample appointments |
| `/patients` | Patients | Search and manage sample patient records |
| `/doctors` | Doctors | Review and manage sample doctors and working hours |
| `/services` | Services | Review and manage sample clinic services |
| `/availability` | Availability | Edit clinic hours and blocked dates; preview bookable slots |
| `/conversations` | Conversations | Read sample patient/assistant conversation history |
| `/analytics` | Analytics | Review charts and metrics derived from sample records |
| `/settings` | Settings | Edit sample clinic, assistant, notification, and admin preferences |
| `/help` | Help & Support | Read FAQs, contact information, and reset the demo workspace |

`/login` is an additional informational demo entry screen. Google sign-in is disabled.

### Demo data and persistence

- Seed records are generated by `src/services/demo/seed.ts`.
- The demo store lives in browser application memory through `src/services/demo/store.ts`.
- User changes are interactive but reset when the application reloads; they are not saved to a database or shared between users.
- Screens that present sample records display a Demo label. Do not describe sample conversations or bookings as live clinic activity.

### Inactive integrations

- **Database and patient records:** Not connected.
- **Authentication:** Not connected; sign-in controls remain disabled.
- **WhatsApp:** Not connected; conversations are read-only sample content.
- **AI assistant:** Not connected; assistant references and replies illustrate intended product behavior only.
- **Gemini and n8n:** Not configured or called by the frontend.

Never imply that a planned integration is active.

## Functional requirements

1. Provide navigation among all ten dashboard routes through the shared dashboard shell.
2. Keep the shell mounted across dashboard route navigation; render `/login` without it.
3. Show route-specific titles and metadata under the Arovia Healthcare Dashboard brand.
4. Support the existing sample-data workflows and service actions without introducing a mock network/backend.
5. Enforce scheduling rules in pure functions in `src/lib/scheduling.ts`: clinic opening sessions, doctor working hours, blocked dates, and double-booking limits.
6. Clearly identify demo records and show inactive integrations as **Not connected**.
7. Support a reset to the original demo dataset from Help & Support.
8. Keep the application operable using its responsive layout and existing component behavior.

## Non-functional requirements

- Preserve the current visual identity, layout, navigation, typography, colors, and animations when making infrastructure changes.
- Use strict TypeScript settings, including `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`.
- Keep secrets out of browser bundles and browser-accessible environment variables.
- A local developer must be able to install dependencies, run tests, build, and start the application with npm.
- Use semantic HTML, accessible controls, visible focus states, and appropriate labels on interactive controls.

## Acceptance criteria

- `npm install` completes, `npm test` passes, and `npm run build` succeeds.
- `npm run dev` serves the app locally.
- All ten dashboard routes load with the expected page heading and shared dashboard navigation.
- Demo data is labeled as sample data, resets as documented, and is not represented as persisted clinic data.
- No connection to Lovable, Supabase, n8n, WhatsApp, Gemini, or an authentication provider is required to run the current demo.

## Out of scope for this release

- Production patient data storage, synchronization, or backups.
- User accounts, Google sign-in, access control, and clinic tenancy.
- Sending or receiving WhatsApp messages.
- Live AI-generated responses or Gemini API calls.
- Deployment, billing, audit logging, and production compliance certification.

## Future integration direction

Future Supabase, n8n/WhatsApp, and Gemini work requires a separately approved implementation. Database access, authentication and authorization, webhook verification, and model API calls must be implemented through trusted server-side workflows. Do not put service-role credentials, API keys, or webhook secrets in client code.
